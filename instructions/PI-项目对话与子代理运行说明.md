# Pi 项目对话与子代理运行说明

版本：2026-10-29

**一句话：你只面对一个项目主对话；主对话按需找临时帮手，把结果验收后再交给你。**

状态说明：三份插件及调度规则已在本机配置，扩展加载和模拟子进程检查已通过；真实模型委派、多项目 Telegram 路由和长期记忆效果尚未验证。是否已在当前 Pi 会话完成原生重载，也未确认。下文的任务案例是运行方式示意，不是已执行记录。

---

## 1. 你实际怎么使用

例如，你有两个项目：

```text
项目 A：网站开发
└─ 一个主对话
   └─ 只围绕这个网站推进工作

项目 B：Minecraft 实验
└─ 另一个主对话
   └─ 只围绕 Minecraft 推进工作
```

进入项目 A 的对话后，你直接说：

> 给网站加一个登录功能，先看现有代码，完成后测试。

你不必再分别告诉“研究 agent”“代码 agent”“远程 agent”做什么，也不必在几个聊天之间转发结果。

主对话自己决定：哪些工作直接做，哪些交给临时帮手，以及什么时候需要你的确认。

**“自动调用”由模型根据规则判断，不是每条消息都会触发一套固定流程。** 改一行文字通常直接完成；大范围调查、复杂实现或高风险变更才更值得委派。

## 2. 整体结构

```text
你
└─ 项目主对话
   ├─ 自己理解需求、做决定、整合结果
   ├─ fork：带项目上下文执行具体任务
   ├─ advisor：独立分析架构或产品选择
   ├─ reviewer：独立检查实现和风险
   └─ 观察记忆：整理历史，必要时回查来源
```

这里没有重新建立一个常驻团队：

- 不使用 Intercom。
- 不要求你提前开好一排角色聊天。
- 子任务通常做完即结束，不在后台自行领取下一个任务。
- 主对话仍对最终交付负责，不能把子代理的一句“完成”当成验收。

## 3. 三种帮手有什么不同

### 3.1 fork：带着当前背景去干活

适合调查代码、实现独立模块、定位复杂问题、运行测试等工作。

启动时，它获得主对话**当前活动分支的上下文快照**。因此不用把所有背景从头解释一遍。

例如主对话可以派出：

> 检查登录流程涉及哪些文件，找出会话失效的原因。不要改文件，返回证据和建议修复位置。

fork 在自己的 Pi 子进程里读取文件、尝试思路、处理命令输出，再把有用结论交回主对话。主对话不用接收每一次搜索和每一条冗长日志。

注意：

- 这是启动时的快照，不是共享的实时聊天窗口。
- fork 启动后，主对话的新消息不会自动同步给它。
- 子进程修改了项目文件，主对话能看到这些文件变化；这和共享聊天记忆是两回事。
- 当前配置不让子进程加载 Telegram 等扩展，也不让它继续调用委派工具。

### 3.2 advisor：干净上下文里的第二意见

适合架构、产品方案和重要取舍。

它由 `subagent` 工具启动，不复制主对话历史。主对话必须交给它一份完整但精简的任务书，包括目标、必要事实、相关路径、限制和需要回答的问题。

例如：

> 作为架构顾问，对比当前项目采用服务端会话和 JWT 的利弊。读取指定文件，不修改代码，给出建议、依据和未知条件。

默认只提供读取和查找工具，不能直接改代码或运行命令。

它的价值是减少对主对话既有判断的依赖，**并不意味着绝对客观或一定更正确**。默认仍使用同一个模型，不会为了“第二意见”擅自换提供商。

### 3.3 reviewer：干净上下文里的独立审查

同样通过 `subagent` 启动，但任务重点是检查实现：

- 是否正确满足需求；
- 是否存在安全或回归风险；
- 测试是否覆盖关键行为；
- 用户体验是否有明显问题。

例如：

> 审查登录相关的变更，重点检查会话固定、退出登录、错误反馈和测试遗漏。只读，按严重程度报告问题及文件位置。

reviewer 默认只读。它发现问题后交回主对话，由主对话决定修复或向你解释取舍，不自行扩大修改范围。

**advisor 和 reviewer 是每次任务的职责，不是两个永久运行的人格，也不是两套独立的账号。**

## 4. 一次任务如何流转

以“新增登录功能”为例，可能出现下面的流程：

```text
你提出需求
   ↓
主对话检查项目与限制
   ↓
必要时用 fork 调查现有实现
   ↓
遇到关键取舍，再请 advisor 给第二意见
   ↓
主对话或承担明确文件范围的 fork 实现功能
   ↓
运行测试，必要时请 reviewer 独立审查
   ↓
主对话检查实际改动、修复问题、验证结果
   ↓
向你报告完成项、测试结果和剩余风险
```

这不是强制流水线。没有架构取舍就不必调用 advisor；简单修改也不需要完整走一遍。

可以并行的是互不依赖的工作，例如一个帮手调查接口，另一个检查测试。通常最多同时派两个。

如果允许子代理写文件，主对话必须先划分文件归属，避免自己和子代理同时修改同一个文件。存在依赖的步骤则按顺序执行。

## 5. 记忆如何工作

这里使用 `pi-observational-memory`，主要保存两种内容：

- **观察（observation）**：发生了什么、用户决定了什么、测试实际得到了什么结果。
- **提炼（reflection）**：从观察中整理出的较稳定事实、约束或经验。

```text
对话和工具结果逐渐积累
   ↓
达到阈值后，记忆工作模型整理观察与提炼
   ↓
需要压缩上下文时，提供整理后的记忆
   ↓
关键细节不清楚时，用 recall 回查对应来源
```

当前配置的大致节奏是：

- 观察触发阈值：10,000 tokens；
- 提炼触发阈值：20,000 tokens；
- 主动压缩阈值：81,000 估算源内容 tokens；
- 观察单次输入块上限：12,000 估算 tokens；
- 记忆工作模型沿用当前会话模型，调试日志关闭。

这些阈值的统计口径并不完全相同；Pi 原生的上下文窗口压力压缩仍独立存在。它们不是“到某个精确聊天字数就一定执行一次”的承诺。

记忆整理会产生额外模型调用和费用。它不是另一个常驻聊天，也不是全局知识库。

### 记忆的边界

- 记忆属于会话和分支，不自动把项目 A 的内容带到项目 B。
- 摘要会遗漏，模型也可能理解错误；不能承诺“永不遗忘”。
- 重要约束、路径、错误和决策理由，应回查来源，不能只相信一句总结。
- 已补充延迟写入检查，避免在已观察到的会话／分支切换后把旧结果写进新上下文；这不等于取消所有已发出的模型请求。
- 当准备好的观察没有覆盖将被压缩的源内容时，退回 Pi 原生摘要，不直接用那一小部分观察替代整段历史。
- 代码、文档、测试和 Git 仍是持久交付依据；记忆不能替代它们。

## 6. 项目和 Telegram 对话怎样对应

关键是 **Pi 的工作目录**，不是聊天标题。

最直接的方式是在各项目目录启动各自的 Pi：

```sh
cd /实际路径/project-a
pi
```

另一个项目在另一个终端启动：

```sh
cd /实际路径/project-b
pi
```

若使用 Telegram，相应聊天或话题还要通过桥接的路由功能，绑定到对应项目的 Pi 实例。

**仅新建一个 Telegram 对话、改一个聊天名称，不会自动切换工作目录。**

目前只完成了核心插件与规则配置，没有自动创建项目聊天、移动旧会话，或调整你现有的 Telegram 路由。这一步需要先知道你的项目路径及希望采用的对话组织方式。

## 7. 哪些事仍然需要你的授权

自动委派不等于自动扩大权限。

涉及部署、远程机器、安装、删除、发布、凭据或其他超出原任务的操作时，仍须遵守原有授权限制。主对话不能通过把任务交给子代理来绕过确认。

也要区分两种“隔离”：

- **上下文分离**：子代理有自己的对话内容。
- **系统隔离**：限制进程能读哪些文件、访问什么网络、执行什么操作。

当前这套子代理主要解决前一种问题。工作目录限制和工具白名单不是操作系统沙箱。允许使用 shell 的子代理，仍拥有启动 Pi 的用户账号所具备的系统权限。

## 8. 与旧架构相比，具体改变了什么

旧方式的主要组织单位是“职能”：研究、代码、远程、搜索各有自己的工作区或聊天，再由协调者传递信息。

新方式的主要组织单位是“项目”：每个项目有一个主对话，由它按需派出临时帮手，并负责验收。

旧目录、研究资料、工具、代码和操作记录仍然保留，可以在任务确实需要时使用；**目录存在不代表对应 agent 正在运行，也不代表它会被自动启动。**

本次没有安装文章里的 codemapper 或 RTK 优化，先保留核心组合。

## 9. 如何启用和确认

1. 在 Pi 终端重启，或执行原生 `/reload`。
2. 建议在实际项目目录开启一个干净的新会话，不把庞大的旧协调对话直接当成所有项目的共同历史。
3. 检查工具是否出现，再做一次小型真实委派验证。
4. 如需 Telegram 使用，再确认对话路由与项目工作目录相符。

可在原生 Pi 界面使用：

- `/subagents`：查看独立子任务状态；
- `/om:status`：查看记忆状态和工作模型错误；
- `/om:view full`：查看记录的记忆；此命令也会尝试复制到剪贴板。

Telegram 中发送字面上的 `/reload`，不代表已经执行了原生 Pi 重载。

### 当前证据能说明什么

已通过的离线检查包括：三份扩展可被 Pi 1.3.0 加载、fork 快照与独立上下文的区别、子进程启动参数、错误和空输出不算成功、等待结束事件、工作目录与工具限制，以及部分记忆压缩回退。

这些检查使用模拟子进程，**没有调用模型 API**，因此不能证明真实提供商调用、自动调度质量、多项目 Telegram 路由或数周记忆效果已经成功。

## 10. 你只需记住的使用原则

> 进入对应项目的主对话，直接说清目标和限制。让主对话决定是否找帮手；最后检查它交付的实际结果，而不是看它启动了多少个 agent。
