# 我的 Pi Agent 架构

一套「一个项目一个主对话」的代理工作体系：主对话只负责理解需求、拆解派工、做决策和验收，真正干活的是干净上下文的子代理；多个项目由一个确定性协调器统一路由。本站是这套体系的文档门户，全部内容提炼自仓库真实素材。

## 一图流架构

```text
                          用户
                （提需求 · 做决策 · 最终验收）
                            │
 ┌──────────────────────────▼───────────────────────────┐
 │            主对话 primary（每项目一个，cwd = 项目根）     │
 │        只做：需求理解 / 拆解派工 / 决策 / 验收 / 集成      │
 └──────┬─────────────┬─────────────┬──────────────┬─────┘
        │ fork        │ subagent    │ subagent     │ observational
        │ 继承完整对话  │ 干净上下文    │ 干净上下文     │ memory
        ▼             ▼             ▼              ▼
   上下文密集型工作   顾问 / 评审    9 类角色 worker   会话内观察与回忆
 （调试·多文件实现）（只建议不执行）（scout…designer）（非全局知识库）

 ═══════════════════ 跨项目协调层 ═══════════════════════════
   项目 A 主对话 ──┐
   项目 B 主对话 ──┼──▶ pi-project-coordinator
   项目 C 主对话 ──┘    registry · 确定性路由 · 每项目单写队列
                       任务日志 journal · RPC 运行时 · 崩溃语义
```

## 核心理念：委派 → 路由 → 验收 闭环

1. **委派（zero inline execution）**：主对话不亲手干活——包括琐碎任务（2026-11-05 用户明确废止了"琐碎例外"）。实现、测试、调研、评审、部署全部派给子代理，每个任务有界、有书面任务书、有固定验收标准。
2. **路由**：动手前先声明任务类别、执行者与交付物。默认按 9 个预定义角色路由；有界且可本地验证的任务默认 best-of-N 并行——N 个候选各在隔离副本上、用同一套固定验收标准工作，主对话逐一验证、择优采纳；`fork` 只留给真正依赖当前对话上下文的活。
3. **验收闭环**：子代理报 PASS 不算数——主对话亲自看 diff、跑测试、核对证据；失败如实上报，验收标准永不放宽。验证过的经验沉淀进知识库，角色档案随结果持续改进。

## 关键数字

- **9 个预定义角色**：scout / planner / coder / operator / reviewer / researcher / visualizer / writer / designer——全部是任务书模板而非常驻进程，不加载扩展，靠「先读自己的 skill 文件」注入方法论。
- **1 个多项目协调器**：SQLite 持久化（单 WAL 库、零依赖）、每项目 FIFO 队列 + 单写租约、全局并发上限 2、变更类任务崩溃后永不盲目重放。
- **2 层知识库**：`wiki/`（外部一手经验，带置信度）+ `daily/` 与 `knowledge/concepts/`（内部工程日志），scope gate fail-closed，另有可选的 SQLite FTS5 全文检索。
